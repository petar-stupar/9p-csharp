Normative, language-neutral reference for every implementation in this workspace. It was written
from the primary sources vendored under [sources/](sources) (fetched 2026-09-05), not from memory,
and every claim below can be checked against the file it names. Where a source is silent or the
sources disagree, the **Decisions** in [ARCHITECTURE.md](ARCHITECTURE.md) settle it and are marked
`[D]` here. Golden bytes for every message type are in
[fixtures/wire-vectors.json](fixtures/wire-vectors.json), generated by

Terminology: **T-message** = request, **R-message** = reply, **transaction** = the pair. A
**dialect** is one of `9P2000`, `9P2000.u`, `9P2000.L`. "9P2000.uL" is this workspace's umbrella
name for "implements all three" and is **never sent on the wire** `[D]`.

---

## 1. Wire conventions

- Integers `name[1]`, `name[2]`, `name[4]`, `name[8]` are unsigned, **little-endian** (intro(5)).
- `name[s]` is a string: `len[2]` followed by `len` bytes of **UTF-8**, no terminator. NUL is illegal
  inside any 9P string (intro(5)). Maximum length is 65535 bytes by construction.
- `name[n]` with `n[2]` or `n[4]` preceding is a byte blob of `n` bytes (`stat[n]`, `data[count]`).
- `qid[13]` = `type[1] version[4] path[8]`.
- Every message: `size[4] type[1] tag[2] …` where `size` **includes the four size bytes**. Minimum
  legal size is 7 (`P9_HDRSZ`, `linux-9p.h:361`).
- Constants (`plan9-fcall.h`, `linux-9p.h`):

| Name | Value | Meaning |
| --- | --- | --- |
| `NOTAG` | `0xFFFF` | Tag used for `Tversion`/`Rversion` (version(5): "should be"; accept any tag `[D]`) |
| `NOFID` | `0xFFFFFFFF` | "No fid": `afid` when not authenticating |
| `NONUNAME` | `0xFFFFFFFF` | `.u`/`.L` `n_uname` "unspecified" |
| `MAXWELEM` | 16 | Max `nwname`/`nwqid` per `Twalk`/`Rwalk` |
| `IOHDRSZ` | 24 | Header room reserved for `Twrite`/`Rread`; `max payload = msize − IOHDRSZ` |
| `READDIRHDRSZ` | 24 | Same for `Rreaddir` (`linux-9p.h:367`) |
| `ERRMAX` | 128 | Conventional cap on `ename` length (error(5)); clients may truncate to `ERRMAX−1` |
| `STATFIXLEN` | 49 | Fixed part of a 9P2000 stat record incl. its leading `size[2]` (`fcall.h`) |

Actual 9P2000 `Rread` header is 11 bytes and `Twrite` header 23 bytes; `IOHDRSZ` = 24 is the
conventional over-estimate every implementation uses (`srv.c:478`, `srv.c:522`).

## 3. Message layouts

`[s]` string, `[n]` counted blob. Base layouts from intro(5); `.L` from diod. The `.u` deltas come
from the draft's **§7** (§7.1 version, §7.3 auth/attach, §7.4 create, §7.5 stat); §2.2's synopsis is
**not** authoritative for auth/attach, because it reprints `Tauth`/`Tattach` **without**
`n_uname[4]` while §7.3 defines them with it — an internal inconsistency in the draft. §7.3 wins,
and it is what Linux and diod (`diod-9P2000.L-protocol.md:110–113`) implement.

`Tfsync` has two forms in the wild, and the sources differ:

- **diod carries `datasync[4]`** — `diod-9P2000.L-protocol.md:343`:
  `size[4] Tfsync tag[2] fid[4] datasync[4]`; the frame is 15 bytes. Linux's v9fs client sends the
  same shape (`net/9p/client.c` `p9_client_fsync`; not vendored here).
- **hugelgupf/p9 v0.4.1 sends and expects only `fid[4]`** — `hugelgupf-p9-messages.go:1678–1692`:
  `type tfsync struct { fid fid }`, whose `decode` reads `b.ReadFID()` and nothing else and whose
  `encode` writes `b.WriteFID(t.fid)` and nothing else. Its frame is 11 bytes.

`[D]` Our **encoders always emit `datasync[4]`** (the 15-byte frame, diod's layout). Our
**decoders accept both** the 15-byte and the 11-byte frame, defaulting `datasync` to 0 for the
short one, rather than rejecting the short frame under §8 rule 2's trailing/short-field check —
this is the one place a missing fixed-width trailing field is legal, and it is legal for `Tfsync` only (§8 rule 2 names the exception). Both
frames are golden vectors (`Tfsync` and `Tfsync (no datasync)`). Interop caveat: p9ufs decodes only
the 11-byte form, so the four trailing bytes of our `Tfsync` are unread by it and p9's handling of
trailing bytes is not in the vendored sources — recorded in
[fixtures/conformance.md](fixtures/conformance.md).

## 4. Data structures

### 4.1 Qid

`type[1] version[4] path[8]`. `path` is unique per file in the hierarchy for the lifetime of the
server; a file deleted and recreated with the same name **should** get a different path
(intro(5)). `version` typically increments on every modification. Two files are the same iff their
qids are equal.

Qid type bits (`libc.h:570`, `linux-9p.h:344`; the `.u` bits are Linux's):

| Bit | Name | Meaning |
| --- | --- | --- |
| 0x80 | `QTDIR` | directory |
| 0x40 | `QTAPPEND` | append-only |
| 0x20 | `QTEXCL` | exclusive use |
| 0x10 | `QTMOUNT` | mounted channel |
| 0x08 | `QTAUTH` | authentication file (afid) |
| 0x04 | `QTTMP` | not backed up |
| 0x02 | `QTSYMLINK` | symbolic link (`.u`; diod shows `'L'` for it) |
| 0x01 | `QTLINK` | hard link (`.u`) |
| 0x00 | `QTFILE` | plain file |

The two low bits are the one place the sources conflict: the `.u` draft's `qid.types` enum defines
`QTLINK = 0x02` and has **no** `QTSYMLINK` at all, while Linux (`linux-9p.h:350–351`) defines
`QTSYMLINK = 0x02` and `QTLINK = 0x01`. **Linux wins** `[D]` — every `.u`/`.L` peer this workspace
interoperates with is Linux-derived, and the table above is Linux's.

The qid type byte **must** equal the top 8 bits of the file's mode word (`stat(5)`: "represented as
a bit vector corresponding to the high 8 bits of the file's mode word"). In `.L` the qid type is
derived from the POSIX file type; **our rule** `[D]` is `S_IFDIR → QTDIR`, `S_IFLNK → QTSYMLINK`,
everything else → `QTFILE`. hugelgupf/p9 deviates for special files: `FileMode.QIDType()`
(`hugelgupf-p9-p9.go:165–177`) returns `TypeDir` for directories, `TypeSymlink` for symlinks,
`TypeAppendOnly` (0x40) for sockets, named pipes and character devices — the comment on that branch
reads "Best approximation" — and `TypeRegular` only for the remainder. A client must therefore not
read "append-only" out of a `.L` peer's qid; in `.L` the authority for the file type is
`Rgetattr.mode` (§4.7), and the qid type is a hint.

### 4.2 Stat record (9P2000 / .u)

```text
size[2]  total byte count of the following data (excludes itself)
type[2]  for kernel use            dev[4]      for kernel use
qid[13]  see §4.1                  mode[4]     permissions and flags (§4.4)
atime[4] seconds since epoch       mtime[4]    seconds since epoch
length[8] bytes; 0 for directories
name[s]  "/" for the server root   uid[s] gid[s] muid[s]   textual owner, group, last modifier
--- 9P2000.u appends: ---
extension[s]  symlink target, or "b maj min" / "c maj min" for devices, "" otherwise
n_uid[4] n_gid[4] n_muid[4]  numeric ids; NONUNAME (~0) when unknown
```

A stat record is at most 65535 bytes (stat(5)). Directory reads in 9P2000/.u return **an integral
number of records**; a record is never split across `Rread` boundaries (read(5)).

`Twstat` "don't touch" values (stat(5)): every integer field `~0` of its width (`type 0xFFFF`,
`dev 0xFFFFFFFF`, `qid.type 0xFF`, `qid.version 0xFFFFFFFF`, `qid.path 0xFFFF…`, `mode`, `atime`,
`mtime` `0xFFFFFFFF`, `length 0xFFFF…FFFF`) and every string empty. A `Twstat` whose fields are
**all** don't-touch is a request to commit the file to stable storage (fsync). A `wstat` is atomic:
all changes or none.

### 4.3 9P2000.L directory entry (`Rreaddir.data`)

`qid[13] offset[8] type[1] name[s]`. `type` is the POSIX `d_type` (`DT_DIR=4`, `DT_REG=8`,
`DT_LNK=10`, … — Linux uapi `dirent.h` values, not vendored here). `offset` is the cookie to pass
as `Treaddir.offset` to continue **after** this entry; the first call uses 0. A reply with
`count = 0` means end of directory. Entries are never split.

Real `.L` servers over a real directory do emit `.` and `..`: diod's own trace
(`diod-9P2000.L-protocol.md:472–473`) shows the first `Rreaddir` carrying `.`
(`… 04 0100 2e …`) and `..`. Synthetic servers in this workspace **do not** emit `.`/`..` in
`Rreaddir` `[D]`, and never emit them in 9P2000 `Rread` of a directory (intro(5): directories
"contain no explicit entry for `..` or `.`"). Observable consequence, stated so nobody reports it as
a bug: `ls -a` on a v9fs mount of one of our servers shows no `.`/`..` entries. Walking to `..` is
unaffected — that is `Twalk`, not a directory listing.

### 4.4 Mode bits (9P2000 / .u stat.mode, Tcreate.perm)

| Bit | Name | Dialect | Meaning |
| --- | --- | --- | --- |
| 0x80000000 | `DMDIR` | all | directory |
| 0x40000000 | `DMAPPEND` | all | append-only (offset ignored on write; OTRUNC ignored) |
| 0x20000000 | `DMEXCL` | all | exclusive use (one open fid at a time) |
| 0x10000000 | `DMMOUNT` | all | mounted channel |
| 0x08000000 | `DMAUTH` | all | authentication file |
| 0x04000000 | `DMTMP` | all | not backed up |
| 0x02000000 | `DMSYMLINK` | `.u` | symbolic link; `extension` holds the target |
| 0x01000000 | `DMLINK` | `.u` (Linux) | hard link |
| 0x00800000 | `DMDEVICE` | `.u` | device; `extension` = `"b maj min"` or `"c maj min"` |
| 0x00200000 | `DMNAMEDPIPE` | `.u` | FIFO |
| 0x00100000 | `DMSOCKET` | `.u` | socket |
| 0x00080000 | `DMSETUID` | `.u` | setuid |
| 0x00040000 | `DMSETGID` | `.u` | setgid |
| 0x00010000 | `DMSETVTX` | `.u` (Linux) | sticky |
| 0x000001FF | permissions | all | `rwx` owner (bits 8–6), group (5–3), other (2–0) |

Bit 28 (`DMMOUNT`) is "skipped for historical reasons" in the qid mirror (intro(5)); qid.type
mirrors bits 31,30,29,(27),26 as `QTDIR QTAPPEND QTEXCL QTAUTH QTTMP`.

### 4.5 Open modes

9P2000/.u `Topen.mode[1]`, `Tcreate.mode[1]` (`libc.h:545`, `linux-9p.h:241`):

| Value | Name | Meaning |
| --- | --- | --- |
| 0 | `OREAD` | read |
| 1 | `OWRITE` | write |
| 2 | `ORDWR` | read+write |
| 3 | `OEXEC` | execute (read with execute permission check) |
| 0x10 | `OTRUNC` | truncate first (needs write permission) |
| 0x20 | `OCEXEC` | close on exec (client-local; servers ignore) |
| 0x40 | `ORCLOSE` | remove when clunked (needs remove permission in the parent) |
| 0x80 | `OAPPEND` | Linux extension (`linux-9p.h:223,248`: "open the file and seek to the end"). A **flag** OR'd with an access mode, not an access mode itself |
| 0x1000 | `OEXCL` | kernel-side create-only hint; never sent in `mode[1]` (does not fit) |

Bits other than the low two and `OTRUNC`/`ORCLOSE` "should be zero" (open(5)). Our servers `[D]`
take the access mode from the **low two bits only**, honour `OTRUNC` and `ORCLOSE`, ignore
`OCEXEC` (client-local), accept `OAPPEND` as a flag that adds append semantics to writes on that
fid without changing the access mode (so `OREAD` plus `OAPPEND` stays a read open, and `OWRITE`
plus `OAPPEND` writes at the end), and reject any other set bit with `Rerror "bad open mode"`. A
directory may only be opened `OREAD`/`OEXEC`; `OTRUNC`/`ORCLOSE` on a directory is an error.

9P2000.L `Tlopen.flags[4]`, `Tlcreate.flags[4]` are **Linux `open(2)` flag values in octal**
(`linux-9p.h:296`): `O_RDONLY 0`, `O_WRONLY 01`, `O_RDWR 02`, `O_NOACCESS 03`, `O_CREAT 0100`,
`O_EXCL 0200`, `O_NOCTTY 0400`, `O_TRUNC 01000`, `O_APPEND 02000`, `O_NONBLOCK 04000`,
`O_DSYNC 010000`, `FASYNC 020000`, `O_DIRECT 040000`, `O_LARGEFILE 0100000`,
`O_DIRECTORY 0200000`, `O_NOFOLLOW 0400000`, `O_NOATIME 01000000`, `O_CLOEXEC 02000000`,
`O_SYNC 04000000`. These are the **generic (x86) values regardless of the peer's architecture**
(v9fs converts through `p9_dotl_flags` in `fs/9p/vfs_inode_dotl.c`; that function is not vendored
here). Servers honour access mode, `O_TRUNC`, `O_APPEND`,
`O_EXCL` (create), `O_DIRECTORY`, `O_NOFOLLOW`; they ignore the rest `[D]`.

`Tunlinkat.flags`: `AT_REMOVEDIR = 0x200` (`linux-9p.h:317`).

Servers must still send the full 160-byte reply; fields not marked valid carry 0. `qid` is always
valid.

`Tsetattr.valid` (32-bit): `MODE 0x01 UID 0x02 GID 0x04 SIZE 0x08 ATIME 0x10 MTIME 0x20 CTIME 0x40
ATIME_SET 0x80 MTIME_SET 0x100`. A time bit without its `_SET` bit means "use server's current
time"; with `_SET`, use the supplied value.

Workspace policy `[D]` (approved 2026-09-10): `valid=0` validates the fid and succeeds without
attribute mutation or fsync. `ATIME_SET` without `ATIME`, or `MTIME_SET` without `MTIME`, is
`EINVAL`, including when other fields are requested; no part of the update is applied and the
connection remains usable. This rejection is a workspace policy, not a requirement stated by diod.
The all-don't-touch `Twstat` fsync convention does not apply to `Tsetattr`; `.L` has `Tfsync`.
A `.L` size update on a directory is `EISDIR`, even for zero. Legacy `Twstat` forbids nonzero
directory length; a zero length remains subject to the handler's own restrictions.

### 4.7 `.L` mode and file types

`Rgetattr.mode`, `Tlcreate.mode`, `Tmkdir.mode`, `Tmknod.mode` are POSIX `st_mode` values (the
constants below are the Linux/POSIX `<sys/stat.h>` values; that header is not vendored here, and
hugelgupf/p9 agrees on the two it defines — `ModeSymlink 0120000`, `ModeDirectory 040000`,
`hugelgupf-p9-p9.go:118,127`):
`S_IFMT 0170000`, `S_IFSOCK 0140000`, `S_IFLNK 0120000`, `S_IFREG 0100000`, `S_IFBLK 060000`,
`S_IFDIR 040000`, `S_IFCHR 020000`, `S_IFIFO 010000`, `S_ISUID 04000`, `S_ISGID 02000`,
`S_ISVTX 01000`, permissions `0777`. `Tlcreate.mode` and `Tmkdir.mode` carry permission bits (the
file type is implied); diod's trace shows v9fs sending `0100644`/`040755` including the type, so
servers **mask with 07777** `[D]`.

### 4.8 Locks (`.L`)

`type`: `RDLCK 0`, `WRLCK 1`, `UNLCK 2`. `Tlock.flags`: `BLOCK 1`, `RECLAIM 2` (reserved).
`Rlock.status`: `SUCCESS 0`, `BLOCKED 1`, `ERROR 2`, `GRACE 3`. `length 0` means "to end of
file". v9fs implements `F_SETLKW` by retrying while `BLOCKED`; servers never block a connection's
reader on a lock `[D]`. `Rgetlock.type = UNLCK` means no conflicting lock.

### 4.9 `Rstatfs`

`type` is the filesystem magic (diod uses the backing fs's; synthetic servers return
`0x01021997`, `V9FS_MAGIC` `[D]` — Linux `include/uapi/linux/magic.h`, not vendored here),
`bsize` block size, `blocks/bfree/bavail` in `bsize` units,
`files/ffree` inode counts, `fsid` opaque, `namelen` max component length (255 `[D]`).

## 5. Semantics

### 5.1 Version (version(5), `.u` §7.1, diod)

- `Tversion` **must be the first message** on a connection; the client sends nothing else until
  `Rversion` arrives. Tag should be `NOTAG`; servers accept any tag and echo it `[D]`.
- `msize` is the maximum total message size either side will send or accept, including the size
  field and excluding transport framing. The server replies with **its** maximum, which **must be ≤
  the client's**. Both sides then honour it. `Rread.count`, `Twrite.count`,
  `Rreaddir.count` are bounded by `msize − IOHDRSZ` (`srv.c:478,522`). If a client asks for more,
  the server silently clamps the count (Plan 9 behaviour) — never errors.
- Version string rules: must start with `9P` (version(5):50–54). If the server does not understand
  the string it replies `Rversion` (never `Rerror`) with the version string `"unknown"`
  (version(5):55–63). The text up to the first `.` names the base version; after stripping any
  period-separated suffix the server may answer with the client's own string or with `9Pnnnn` where
  `nnnn` is less than or equal to the digits the client sent (version(5):64–78). `.u` §7.1: a client
  wanting Unix extensions sends `9P2000.u`; a server that supports them answers `9P2000.u`,
  otherwise `9P2000`. `.L`: diod (`diod-9P2000.L-protocol.md:41–42`) says only that the string must
  be exactly `9P2000.L`; the fallback in which a server without `.L` strips the suffix and answers
  `9P2000` comes from **version(5):70–78**, not from diod. Nothing is claimed here about how a
  client reacts to that downgrade: `linux-v9fs-9p.rst:195–201` documents only the values the
  `version=` mount option takes and says nothing about the client's reaction, and v9fs's client code
  is not vendored. Our own clients' reaction is the last bullet of the algorithm below.
- **Negotiation algorithm** `[D]` for our servers. Let `E` be the **configured dialect set** — the
  `dialects` option of `Server` (ARCHITECTURE.md §4) or `--dialects` on the examples and the cli —
  and let `v` be the client's version string and `m` its `msize`. **A dialect outside `E` is never
  answered with, however the client asks**; every step below is conditioned on `E`:
  1. Reply `msize = min(m, server_max_msize)` (subject to the `msize` policy below).
  2. If `v == "9P2000.L"` **and `9P2000.L ∈ E`** → `"9P2000.L"`.
  3. Else if `v == "9P2000.u"` **and `9P2000.u ∈ E`** → `"9P2000.u"`.
  4. Else if `v` starts with `"9P2000"` (with or without a `.suffix`) **and `9P2000 ∈ E`** →
     `"9P2000"`. This is the version(5):70–78 suffix-stripping fallback. It follows that a server
     configured `--dialects 9P2000.L` answers a plain `9P2000` client with `"unknown"` rather than
     with a dialect it was told not to speak, and a server configured `--dialects 9P2000` answers a
     `9P2000.L` client with `"9P2000"`.
  5. Else → `"unknown"`. In an `"unknown"` reply the server echoes the client's `msize` (it must
     be ≤ the client's per version(5)); the golden `Rversion unknown` vector carries 8192 and
     therefore assumes a client that offered ≥ 8192.

  The negotiation function is unit-tested against a table with one row per (`E`, `v`) pair, over
  `E` ∈ {each of the three singletons, each of the three pairs, all three} and `v` ∈
  {`9P2000`, `9P2000.u`, `9P2000.L`, `9P2000.x`, `9P1000`, `9P3000`, `XYZ`, `""`} — the table
  ARCHITECTURE.md §3 refers to.

  **Before a dialect is agreed there is no agreed error type.** In that state — before the first
  `Tversion`, and after an `Rversion "unknown"` — the connection stays open **for another
  `Tversion` only** `[D]`. Any other message is answered with a **9P2000-shaped `Rerror`**
  (`size[4] Rerror tag[2] ename[s]` and nothing after it: the one error form every 9P peer can
  decode, with no `errno[4]` and never `Rlerror`) carrying the ename `"version not negotiated"`,
  and the connection is **closed** after that reply. §8 rule 9 states the identical rule for the
  pre-`Tversion` state; the two states behave the same and neither is a way to keep a session alive
  without a dialect.

  Our clients send their preferred dialect first and, on `"unknown"` or a downgrade the caller
  did not allow, fail with a typed `VersionError` (never silently downgrade below the caller's
  minimum).
- A successful `Tversion` **aborts all outstanding I/O and clunks every fid** (a new session);
  server implementations reset the fid table and cancel in-flight requests.
- `msize` policy `[D]`: servers refuse `msize < 4096` and cap at a configurable maximum (default
  1 MiB; `.L` peers commonly ask 512 KiB). Clients default to 128 KiB for 9P2000/.u and 1 MiB for
  `.L`. The floor is **4096 because that is the header allowance Linux itself reserves for a
  transfer** (`P9_ZC_HDR_SZ 4096`, `linux-9p.h:370`), not because smaller messages cannot carry a
  `Rstat`: the largest `Rstat` with a 255-byte name is only about 330 bytes and fits easily. Below
  the floor the per-message payload collapses (`msize − IOHDRSZ`) and a transfer costs more in round
  trips than it moves in bytes, so we decline the session rather than serve it badly. The refusal is
  an `Rversion` whose version string is `"unknown"` (version(5):55–63): a server may **not** answer
  with an `msize` larger than the client's (version(5):45–48), so "reply with the floor" is not an
  option, and `Rerror` is forbidden for `version`. Client-visible symptom: the client sees
  `"unknown"` and reports a version/msize mismatch, not a protocol error.

### 5.2 Auth and attach (attach(5), `.u` §7.3, diod)

- Without authentication the client sets `afid = NOFID`. With authentication: `Tauth(afid, uname,
  aname)` → `Rauth(aqid)` with `aqid.type & QTAUTH`; the client then **reads and writes the afid**
  to run an authentication protocol **not defined by 9P** (attach(5):88–105); then
  `Tattach(fid, afid, uname, aname)`.
- A server that does not require authentication refuses `Tauth`. One sentence per dialect:
  **9P2000 and 9P2000.u** — `Rerror` with the ename `"authentication not required"` `[D]`
  (lib9p's own text is `"%s: authentication not required"` with an `argv0` prefix, `srv.c:197`; we
  drop the prefix so the ename does not depend on the program's name). **9P2000.L** — `Rlerror`
  with `ECONNREFUSED (111)` `[D]`; diod (`diod-9P2000.L-protocol.md:117`) prescribes `Rlerror`
  here but names no errno, so the value is ours.
- `Tattach.fid` must not be in use ("An error is returned if fid is already in use"). The reply
  qid is the root of the tree named by `aname` (`""` = default tree).
- An afid is bound at `Tauth` time to the triple **(`uname`, `n_uname`, `aname`)** `[D]`, and the
  same validated afid may be used for several attaches against that triple. attach(5):112–119 binds
  it to "the same `uname` and `aname`"; the triple extends that to `.u`/`.L`, where the identity may
  live in `n_uname` while `uname` is `""` (`diod-9P2000.L-protocol.md:123`, `.u` draft §7.3). A
  `Tattach` presenting the afid must carry a `uname` equal to the afid's **or empty**, and an
  `n_uname` equal to the afid's **or `NONUNAME`**; anything else is rejected. Without the `n_uname`
  half, an afid obtained as `Tauth(uname="", n_uname=1000)` would satisfy a
  `Tattach(uname="", n_uname=1001)` — that is the bypass this rule closes.
- The user an attach runs as is the identity **the authenticator produced over the afid**, never the
  `uname`/`n_uname` the client claimed. The claimed values are only checked for agreement with the
  afid's triple as above; they are an assertion, not a credential. The afid may be clunked after the
  attach.
- `.u`/`.L`: `n_uname[4]` follows `aname`; if not `NONUNAME` it takes precedence over `uname`
  (`.u` §7.3, diod). v9fs `access=user` sends one `Tattach` per Unix user with `uname ""` and
  `n_uname = uid` (diod trace). Servers must therefore accept an empty `uname` when `n_uname` is set.
- The **implicit user** of every later request on a fid is the user of the attach that created it
  (intro(5) "ACCESS PERMISSIONS"); permission checks use that user, never a per-message field.

### 5.3 Flush (flush(5))

- On `Tflush(oldtag)` the server: if `oldtag` is pending, aborts it (best effort) and **must not
  reply to it afterwards**; in every case replies `Rflush` (never `Rerror`) with the flush's own tag.
- A server may reply to the pending request before the `Rflush`; the client must then honour that
  reply as if not flushed (a `Tcreate` may have created, a `Twalk` may have bound a fid).
- Multiple `Tflush` for one tag are answered in order; answering the last implies all earlier.
- The client may not reuse `oldtag` until it has received the `Rflush`. Flushing an unknown tag
  and flushing a `Tflush` are both legal and answered with `Rflush`.
- Server implementation rule `[D]`: `Tflush` is processed **in arrival order relative to the
  request it names** (flush semantics "depend on messages arriving in order"); a request's reply
  and its flush's reply are serialised through one per-connection writer.

### 5.4 Walk (walk(5))

- `fid` must exist, must be a directory if `nwname > 0`, and **must not be open**. `newfid` must be
  unused unless `newfid == fid`; a `newfid` in use draws `Rerror` (`Edupfid "duplicate fid"`).
- `nwname ≤ MAXWELEM (16)`; more is a malformed message (`convM2S.c:131`).
- Elements are walked in order. If the **first** element fails → `Rerror`, nothing changes. If a
  later element fails → `Rwalk` with `nwqid < nwname` holding the qids walked so far; `newfid` is
  **not** bound (and `fid` unaffected). Only `nwqid == nwname` binds `newfid`.
- `nwname == 0` clones `fid` into `newfid`. The fid must not be open, exactly as for a walk with
  elements: walk(5):37–44 requires the fid to be "valid in the current session" and "not have been
  opened for I/O", and `srv.c:302–309` answers `"cannot clone open fid"` when `fid->omode != -1`.
- `".."` in the root walks to the root itself. `"."` is never sent. Names containing `/` or NUL are
  rejected `[D]` (`Rerror "bad name"` / `Rlerror EINVAL`); a synthetic server never interprets
  `..` beyond its own tree.
- A walk requires "execute" (search) permission on each directory traversed.

### 5.5 Open and create (open(5), `.u` §7.4)

- The fid must not already be open; open/create on an open fid is an error.
- Permission checks happen at open time only. `OTRUNC` needs write permission and is ignored for
  `DMAPPEND` files. `ORCLOSE` needs remove permission on the parent.
- `Tcreate`: `fid` is a directory with write permission; after success the **same fid** represents
  the new, opened file. Owner = implicit user, group = directory's group, perms =
  `perm & (~0666 | (dir.perm & 0666))` (files) or `perm & (~0777 | (dir.perm & 0777))` (dirs).
  Names `.`/`..` and an existing name are errors. `DMDIR` in `perm` creates a directory (then
  `mode` must be `OREAD`). `DMAPPEND`, `DMEXCL` and `DMTMP` in `perm` make the file append-only,
  exclusive-use or temporary (open(2)) and reach the handler as `CreateRequest.file_flags`;
  `DMAUTH` and `DMMOUNT` are the server's and are refused (§8 rule 19).
- `iounit` may be 0; if not, it is the max bytes guaranteed to transfer in one message. Our
  servers return `msize − IOHDRSZ` `[D]`.
- `.u`: `Tcreate.extension` — target for `DMSYMLINK`, `"b maj min"`/`"c maj min"` for `DMDEVICE`,
  `""` otherwise. `DMNAMEDPIPE`/`DMSOCKET` need no extension.
- `.L` `Tlopen`/`Tlcreate` use POSIX flags (§4.5); `Tlcreate.gid` is the caller's effective gid,
  and `flags` carries the caller's open intent (diod ignores it; we honour `O_TRUNC`, `O_EXCL`,
  `O_APPEND` and the access mode `[D]`).
- `DMEXCL`: only one open fid across all clients; a second open draws an error. Servers may break
  the lock after minutes of inactivity.

### 5.6 Read and write (read(5))

- `Tread` needs a fid opened for reading (`OREAD`/`ORDWR`/`OEXEC`); `Twrite` needs `OWRITE`/`ORDWR`.
- `Rread.count ≤ Tread.count`; `count = 0` at or past EOF. `Rwrite.count` = bytes written; less
  than requested is "usually an error" for the client.
- Directory read (9P2000/.u): whole stat records only; `offset` must be 0 or `previous offset +
  previous count` — any other offset is `Rerror` (`Ebadoffset "bad offset"`). Directories cannot be
  written.
- Append-only files ignore `offset`.
- Servers clamp `count` to `msize − IOHDRSZ`; they never send a reply larger than `msize`.

### 5.7 Clunk and remove (clunk(5), remove(5))

- `Tclunk` frees the fid **even if it replies with an error**; the fid may be reused afterwards. A
  fid opened with `ORCLOSE` removes its file on clunk.
- `Tremove` = clunk with the side effect of removing the file if the user has write permission in
  the parent. The fid is freed **even if the remove fails**. Removing a non-empty directory is an
  error `[D]` (`"directory not empty"` / `ENOTEMPTY`). Effect on other fids of the same file is
  implementation-defined.

### 5.8 Stat and wstat (stat(5))

- `Tstat` needs no permission. `Twstat` rules: `name` — write permission in the parent, target
  must not exist; `length` — write permission on the file, directories must stay 0; `mode`,
  `mtime` — owner or group leader; `gid` — owner who is a member of the new group; **owner (uid)
  cannot change**; the `DMDIR` bit cannot change; `atime`, `muid`, `qid`, `type`, `dev` cannot be
  set. Atomic: all or nothing. The `DMAPPEND` / `DMEXCL` / `DMTMP` bits of `mode` are settable —
  stat(5): the directory bit is the one mode bit a wstat cannot change — and reach the handler as
  `SetAttr.flags` when they differ from the file's own; `DMAUTH` / `DMMOUNT` cannot be set; §8
  rule 19.
- `.u` `stat` appends `extension n_uid n_gid n_muid`; `Twstat` may set `n_uid`/`n_gid` under the
  same rules as `uid`/`gid`.

### 5.9 9P2000.L semantics (diod)

- `Rlerror.ecode` is a **Linux errno** number. Servers never send `Rerror` in a `.L` session.
- `Tgetattr`/`Tsetattr` per §4.6. `Treaddir` requires the fid to have been `Tlopen`ed; `offset` is
  the last returned entry's cookie; `count = 0` ends the listing.
- `Tlink(dfid, fid, name)`: hard link to `fid` named `name` in `dfid`. `Tsymlink(fid=dir, name,
  symtgt, gid)`. `Tmknod(dfid, …)`. `Tmkdir(dfid, name, mode, gid)`.
- `Trename(fid, dfid, name)` renames the object `fid` refers to into directory `dfid`; superseded
  by `Trenameat(olddirfid, oldname, newdirfid, newname)`; a server answering `ENOTSUPP`
  (`EOPNOTSUPP`, 95) to `Trenameat` makes v9fs fall back to `Trename`. Likewise `Tunlinkat` →
  `Tremove`. Our servers implement **both** forms `[D]`.
- `Tunlinkat(dirfd, name, flags)` does **not** clunk any fid referring to the file.
- `Txattrwalk(fid, newfid, name)` binds `newfid` to the xattr (empty name = the list) and returns
  its size; then `Tread` on `newfid`. `Txattrcreate(fid, name, attr_size, flags)` turns `fid` into
  an xattr sink; the value is `Twrite`n and committed **on clunk**; a byte count ≠ `attr_size` is an
  error at clunk. `flags`: `XATTR_CREATE 1`, `XATTR_REPLACE 2`.
- `Tfsync(fid, datasync)`; `Tstatfs(fid)`; `Tlock`/`Tgetlock` per §4.8.
- Errno values used by this workspace's synthetic servers `[D]`: `EPERM 1, ENOENT 2, EIO 5,
  EBADF 9, EACCES 13, EEXIST 17, ENOTDIR 20, EISDIR 21, EINVAL 22, EFBIG 27, ENOSPC 28,
  EROFS 30, ENAMETOOLONG 36, ENOSYS 38, ENOTEMPTY 39, ELOOP 40, ENODATA 61, EPROTO 71,
  EOVERFLOW 75, EOPNOTSUPP 95, ECONNREFUSED 111, ENOLCK 37, EAGAIN 11, ERANGE 34, ENOMEM 12,
  ENFILE 23`. `ENFILE` is the per-connection fid-table cap of §8 rule 7; `ECONNREFUSED` is the
  `.L` refusal of `Tauth` (§5.2); `ENOMEM` is for genuine allocation failure only, never for a
  cap that the server chose.

| Concern | 9P2000 | 9P2000.u | 9P2000.L |
| --- | --- | --- | --- |
| Error reply | `Rerror ename[s]` | `Rerror ename[s] errno[4]` | `Rlerror ecode[4]` |

| Rename | `Twstat.name` (same dir) | same | `Trename`, `Trenameat` |

| Users | textual | textual + numeric | numeric only (`uid`/`gid` in getattr) |
| Locks / xattr / fsync / statfs | none | none | `Tlock Tgetlock Txattr* Tfsync Tstatfs` |
| Canonical peers | Plan 9, plan9port `9p`, u9fs | Linux v9fs `version=9p2000.u`, u9fs, QEMU | Linux v9fs (default), diod, hugelgupf/p9, QEMU virtio-9p |

## 7. Unified attribute model `[D]`

Every server handler in this workspace produces one dialect-neutral `Attr` and the protocol layer
projects it (see ARCHITECTURE.md "Handler model"):

```text
Attr { qid; kind: dir|file|symlink|fifo|socket|chardev|blockdev; perm: u32 (0777 + suid/sgid/sticky);
       flags: append|excl|tmp|auth; nlink; uid_name; gid_name; muid_name; uid; gid; rdev: (major, minor);
       size; blksize; blocks; atime, mtime, ctime, btime: (sec, nsec); gen; data_version; symlink_target }
```

| `Attr` | 9P2000 stat | `.u` stat | `.L` getattr |
| --- | --- | --- | --- |
| kind=dir | `DMDIR`, `QTDIR` | same | `S_IFDIR`, `QTDIR` |
| kind=symlink | not representable → `Rerror "symlinks not supported"` on stat; walk **through** it is server-side | `DMSYMLINK`, `QTSYMLINK`, `extension=target` | `S_IFLNK`, `QTSYMLINK`, `Treadlink` |
| kind=fifo/socket/dev | not representable (plain file) | `DMNAMEDPIPE`/`DMSOCKET`/`DMDEVICE` + `extension` | `S_IFIFO`/`S_IFSOCK`/`S_IFCHR`/`S_IFBLK`, `rdev` |
| flags | `DMAPPEND DMEXCL DMTMP DMAUTH` + qid bits | same | qid bits only (`DMAPPEND` → `O_APPEND` semantics) |
| perm high bits | dropped | `DMSETUID DMSETGID DMSETVTX` | `S_ISUID S_ISGID S_ISVTX` |
| users | `uid gid muid` names | names + `n_uid n_gid n_muid` | `uid gid` numbers |
| times | `atime mtime` seconds | same | `atime mtime ctime btime` sec+nsec |
| size | `length` (0 for dirs) | same | `size`, `blksize`, `blocks` |

`Twstat` → `SetAttr{name?, perm?, mtime?, gid?, length?, (u: n_gid?)}`; `Tsetattr` →
`SetAttr{perm?, uid?, gid?, size?, atime?, mtime?}`; the handler sees one `SetAttr` type.

## 8. Validation and safety rules (normative for every implementation)

Decoding (per `convM2S.c` and `srv.c`, hardened):

1. Read exactly 4 bytes, `size`; reject `size < 7` or `size > msize` — **close the connection** on
   a size violation; it cannot be resynced. Before a successful `Tversion` there is no negotiated
   `msize`, and the configured **maximum must not be used** as the bound there: an unauthenticated
   peer would make every connection reserve 1 MiB just by lying in the size field. The
   pre-negotiation cap is a small constant, **8192 bytes** `[D]` — a legal `Tversion` is under 300
   bytes — and the first message on a connection must be a `Tversion` (rule 9).
2. Every counted field is bounds-checked against the remaining bytes **before** any allocation;
   `nwname > 16`, `count > size`, string overruns, trailing bytes after the last field, and a
   `stat[n]` whose inner `size[2]` disagrees with `n` are all malformed → `Rerror "protocol botch"` /
   `Rlerror EPROTO` `[D]` and the connection is closed after the reply. Sole exception: a `Tfsync`
   of exactly 11 bytes (no `datasync[4]`) is legal and decodes with `datasync = 0` (§3.4).
3. Strings must be valid UTF-8 and contain no NUL; names in `Twalk`, `Tcreate`, `Tlcreate`,
   `Tmkdir`, `Tsymlink`, `Tmknod`, `Tlink`, `Trename(at)`, `Tunlinkat`, `Txattr*` must not contain
   `/`, and must not be `.`; `..` is legal only in `Twalk`. Max name length 255 bytes `[D]`.
   A nonempty `Twstat.stat.name` is a rename component and follows the same rules; empty means
   "leave unchanged". `Rstat.stat.name` is a label and may be `/` for the root. A configured
   smaller name limit refuses otherwise wire-legal request names with `ENAMETOOLONG` and keeps
   the session usable (conformance F7c); malformed names remain connection-fatal protocol errors.
4. Counted fields must agree with `size`: `Twrite.count` must equal `size − 23` (the `Twrite`
   header is `size[4] type[1] tag[2] fid[4] offset[8] count[4]`), and any counted field that runs
   past the frame is malformed. `msize − IOHDRSZ` is a **service** bound, not a validity bound: a
   maximal legal `Twrite` has `size == msize` and therefore `count == msize − 23`, which is larger
   than `msize − IOHDRSZ`, and it is **not** malformed. The server clamps `Tread.count` and
   `Treaddir.count` to `msize − IOHDRSZ` before filling the reply (`srv.c:478`) and, for a
   `Twrite`, writes at most that many bytes and reports what it wrote in `Rwrite.count`
   (`srv.c:522`) — a short write, not an error.
5. `Twrite.offset + count` and `Tsetattr.size` must not overflow `u64`; `Tlock.start + length` too.

Session state:

6. Tags: a T-message whose tag is already pending draws `Rerror "duplicate tag"` (`Eduptag`) and
   the new request is dropped. `NOTAG` outside `Tversion` is accepted as an ordinary tag `[D]`.
7. Fids: unknown fid → `Eunknownfid "fid unknown or out of range"` / `EBADF`; in-use fid where a fresh one is
   required → `Edupfid`; operations on the afid other than read/write/clunk → error. The
   per-connection fid table is bounded (default 65536 entries `[D]`), and exceeding the cap is one
   condition with **one** answer: `Rerror "Too many open files in system"` in 9P2000/.u, `Rlerror ENFILE (23)` in
   `.L` `[D]`. An afid additionally carries the triple `(uname, n_uname, aname)` it was created
   with (§5.2): a `Tattach` presenting it must match that triple, with an empty `uname` and an
   `n_uname` of `NONUNAME` accepted as "unspecified", and the session's identity is the one the
   authenticator produced, never the claimed `uname`/`n_uname`.
8. Outstanding requests are bounded **twice** `[D]`: per connection (default 256, with 8
   reserved control slots) and per listener (default 4096). An ordinary request that cannot
   acquire both worker budgets immediately is answered `EAGAIN` (`"resource temporarily
   unavailable"` in 9P2000, the same errno in `.u`/`.L`). Release any partially acquired budget.
   Continue receiving and answering `Tflush` while either budget is full; never park the sole
   reader behind an excess ordinary request. `Tflush` itself is not refused for worker overload.
   Replies remain bounded and a peer must read its replies to make transport progress. This
   replaces the former no-refusal backpressure promise (owner decision after review finding C09 of 2026-09-08).
   A budget is returned when the reply is queued, before it can reach the wire, so a client that
   reuses its window the instant it has a reply is never refused for it; a flushed request returns
   its budget when its handler unwinds.
9. A `Tversion` mid-session resets everything (§5.1). Before a dialect has been agreed — before the
   first `Tversion`, and after an `Rversion "unknown"` — the only message the connection accepts is
   a `Tversion`; any other message is answered with a **9P2000-shaped** `Rerror "version not
   negotiated"` (`ename[s]`, no `errno[4]`, never `Rlerror`, because no dialect is agreed and only
   that form is universally decodable) and the connection is then **closed** `[D]`. §5.1 states the
   same rule from the negotiation side.
10. Errors never carry server-internal paths, stack traces, or the untrusted input verbatim beyond
    the ename limit; `ename` is truncated to `ERRMAX − 1` bytes at a UTF-8 boundary.
11. Untrusted strings are never logged raw: escape control characters and cap at 256 bytes.

Client side:

12. Only the client chooses tags and fids; `Tversion` uses `NOTAG`. A reply with an unknown tag,
    an unexpected type (neither `T+1` nor the dialect's error type), or a size > msize is a
    protocol error that terminates the connection.
13. All of these are protocol errors on the client side: an `Rread` whose `count` exceeds the
    `Tread.count` requested, an `Rreaddir` whose `count` exceeds the `Treaddir.count` requested, an
    `Rwrite` whose `count` exceeds the `Twrite.count` sent (a server may report fewer bytes written,
    never more), an `Rwalk` with `nwqid > nwname`, a `stat[n]` with a bad inner size, and an
    `Rreaddir` whose last record is split.
14. After sending `Tflush`, the client waits for `Rflush` before reusing `oldtag`, and delivers an
    earlier-arriving reply to the flushed request normally.

Dialect projection honesty (owner decision of 2026-09-08, after the audit of the C# port; see
ARCHITECTURE.md Decision Log and `backports.md`). The principle behind every rule below: a request
that names something the negotiated dialect, the wire or the handler model cannot carry is
**refused**, never sent or answered with the untranslatable part silently dropped.

15. A client refuses locally what the negotiated dialect cannot express: remove-on-close
    (`ORCLOSE`) in `.L`; `O_EXCL`, `O_DIRECTORY` and `O_NOFOLLOW` in 9P2000 and `.u`; symlink
    creation, statfs, locks and xattrs outside `.L`; a rename across directories in 9P2000 and
    `.u`; and, through `SetAttr`, a textual group or a name in `.L` (`Tsetattr` has neither), a
    numeric gid in plain 9P2000 (`n_gid` is `.u`), and the owner, `atime` or a "server clock" time
    through `Twstat` (§5.8). `EOPNOTSUPP` for an operation the dialect lacks, `EINVAL` for a field
    the message has no slot for, `EPERM` for what stat(5) forbids. In particular a `SetAttr` that
    would project to an all-don't-touch `Twstat` is refused, because that record is an fsync (§4.2).
16. A client sends `OEXEC` in `.L` as `O_RDONLY`: execute permission is the Linux client's
    concern, and access mode 3 is `O_NOACCESS`, which never leaves a client. A data-only sync in
    9P2000 and `.u` is the all-don't-touch `Twstat`; a full sync satisfies a data sync and is not
    a drop.
17. A client reads only the fields an `Rgetattr` marks valid; an unmarked field keeps the `Attr`
    default (`nlink 1`, ids `NONUNAME`, zero times and sizes, kind from the qid). `Attr.Kind` and
    the qid type byte always agree, so a plain-9P2000 qid marked `QTSYMLINK` yields `kind=symlink`.
18. The `Rversion` dialect must be the one the client offered, or `9P2000` for a suffixed 9P2000
    offer; a higher dialect than offered, or any other string, is a version error. An `Rversion`
    that arrives with no `Tversion` outstanding is an unexpected reply under rule 12.
19. `Twstat.mode` and `Tcreate.perm`: the `DMAPPEND`, `DMEXCL` and `DMTMP` bits are honoured —
    open(2) makes them a created file's flags and stat(5) makes the directory bit the one mode bit
    a wstat cannot change — and reach the handler as `CreateRequest.file_flags` and, for a change
    only, `SetAttr.flags` (a bit echoed back unchanged asks for nothing; the flags are part of the
    mode, so the owner rule of §5.8 applies). A handler that cannot give a file the flags refuses
    the whole request; the core reads the file back after the handler answered and refuses with
    `EOPNOTSUPP` when the flags are not there, removing a file it just created, so a success reply
    is never sent for a plain file. `DMAUTH` and `DMMOUNT` are the server's: a create or a change
    asking for either is refused with `EPERM`, never masked away. A file created `DMEXCL` is held
    by its creator from the create (§5.5). The `.u` `DMSETUID` / `DMSETGID` / `DMSETVTX` bits map
    onto the `07777` permission bits and are honoured. Client side: a `Twstat` mode word carries
    the permission bits and the flags together, so a client changing one half reads the record
    first and sends both, as Plan 9's `chmod` and v9fs do; `.L` has no spelling for the three bits
    in `Tlcreate.mode` or `Tsetattr.mode`, and a client refuses them there (rule 15). Decision Log
    2026-09-10; from 2026-09-08 until then the bits were refused with `EPERM`.
20. `Tunlinkat.flags`: `AT_REMOVEDIR` is required for a directory (`EISDIR` without it) and refused
    for anything else (`ENOTDIR`); any other flag bit is `EINVAL`.
21. `Txattrcreate` with `attr_size = 0` **removes** the attribute — it is how v9fs and diod spell
    removexattr — and never sets an empty value.
22. `Rgetattr.valid` marks `btime`, `gen` and `data_version` only when the handler supplied a
    non-zero value: `Attr` has no "unknown", so for those three fields zero is unknown.
23. `Topen` / `Tlopen` on a fid that names a symlink is `ELOOP`; on a fifo, socket or device the
    server cannot open, `ENXIO`. A success reply with no open file behind it is never sent.
    `O_DIRECTORY` on anything but a directory is `ENOTDIR`.
24. A `.u` `Tcreate` with `DMDEVICE` parses `extension` as `"b maj min"` / `"c maj min"` into
    `rdev`; a missing or malformed extension is `EINVAL`.
25. `Tcreate` of a directory whose `mode` carries `OTRUNC` or `ORCLOSE` is refused
    (`"bad open mode"` / `EISDIR`): open(5) forbids both on a directory, and create is judged
    exactly as open.
26. A handler's clunk-time error is the reply's error (`Rerror` / `Rlerror`) with the fid freed
    regardless (§5.7); it is never swallowed into `Rclunk` or `Rremove`.
27. Handlers, the examples included, apply an update whole or refuse it whole (§5.8): a handler
    that honours some `SetAttr` fields refuses the update when a field it cannot honour is set, and
    a truncation it does not perform is refused rather than answered with success.


Lifetime and progress (reference review, 2026-09-08):

28. A fid operation holds a lifetime lease until all its wire/handler work ends. Closing retires
    the fid before waiting for those leases; no new or queued operation may use a retired entry
    or a recycled number. Dispose/clunk must not destroy resources still used by an operation.
    Reset, disconnect and shutdown run the same finalization side effects as explicit clunk:
    remove-on-close, xattr commit and release of exclusive use. Cleanup without a reply logs
    failures and continues through every entry. A cancellation-ignoring handler retains its
    resources until it exits rather than having them disposed underneath it.
29. A high-level xattr write/removal succeeds only after its final clunk is acknowledged.
    Propagate commit errors and timeout; cleanup after an earlier failure preserves that failure.
30. Append-only metadata forces append and ignores truncation after checking the permissions
    required by the requested open. End-of-file selection and writing are atomic across fids.
    A client's append transfer has one outstanding write, retries only an unacknowledged suffix,
    and never replays a later acknowledged chunk. Ordinary offset writes may remain pipelined.
31. Fids retain their full ancestry across separate walks and clones; only the actual attach
    root is its own parent. Protocol rename operations update live aliases and descendants, including moves through
    another fid or connection; rebasing must not let a subtree attach ascend outside its root.
    Each nonempty walk step, including `..`, checks directory type and
    search permission. Any expected filesystem failure after a successful element produces the
    qid prefix and leaves fid bindings unchanged; cancellation/framing errors are not partial success.
32. Plain 9P2000 evaluates the Plan 9 owner/group/other permission alternatives from intro(5).
    Unix dialects use owner, otherwise group, otherwise other class selection. Keep this policy
    in the protocol/core boundary so handlers never need to select a dialect.
33. Reading an xattr value or its name list requires file-read permission before invoking the
    handler. Namespace-specific restrictions may be additional handler policy.
34. A client rejects a nonpositive transfer window before dialing or negotiating. Transfer loops
    independently observe cancellation, including between batches and zero-progress handling.
35. Listener bookkeeping retains active sessions only. TLS/WS/WSS handshakes run independently
    within the underlying connection cap, which includes pending handshakes, completed unclaimed
    connections and delivered live connections. Failed/timed-out handshakes release their slots;
    listener disposal cancels pending work and disposes queued connections. A cancelled individual
    accept does not cancel unrelated handshakes.
36. Custom TLS trust roots retain hostname, chain and application-purpose checks. Require server
    authentication when dialing and client authentication when validating a client certificate;
    a trusted signature does not override a leaf or CA's incompatible extended key usage.
37. A `.L` client whose `Trenameat` is answered `EOPNOTSUPP` retries the rename as `Trename` on
    the walked source, as v9fs does (§5.9); a server implementing only `Trename` (diod 1.0.24) is
    otherwise unusable for renames. A server that refuses both is reported as it answered.
38. An `Rerror` or `Rlerror` carrying `NOTAG` while the client's `Tversion` is outstanding is the
    answer to that `Tversion`: the connection fails with a version error quoting the ename and
    errno, not with the unknown-tag protocol violation of rule 12 (diod answers a dialect it does
    not speak with an `Rlerror` on `NOTAG`).
39. Over 9P2000 and `.u`, every ename a server sends for an errno is a string the Linux kernel's
    `net/9p/error.c` table maps to that errno — the fixture
    [fixtures/linux-9p-errors.json](fixtures/linux-9p-errors.json), generated from the kernel
    source at a pinned commit — so a `version=9p2000` v9fs mount recovers the errno rather than
    `ESERVERFAULT`; every string in that table, and every wording an earlier release of a port
    sent, is understood on receipt. `EOVERFLOW`, which the table lacks, keeps its `strerror` text,
    and the enames of this reference that Linux does not list (`authentication not required`,
    `version not negotiated`) keep their wording. One deliberate override: `authentication failed`
    is `EACCES` on receipt (§5.2), where Linux files it under `ECONNREFUSED`.

40. **Abuse budgets.** A server bounds what a peer may spend, and every bound **refuses rather
    than delays**, so the reader stays free for the `Tflush` that cancels what is already in
    flight. `[D]` (a) An ordinary request past a configured requests-per-second budget, per
    connection or per listener, is answered `EAGAIN`; the burst is the corresponding in-flight
    budget, so a client inside its window is never refused for the rate, and `Tversion` and
    `Tflush` are never metered. (b) Live connections from one peer address are capped; the excess
    connection is accepted — the address is not known before that — and closed at once, while the
    listener-wide cap of rule 8 continues to leave its excess in the kernel's backlog. (c)
    Authentications begun from one address inside a window without one of them reaching a
    successful attach are capped, and past the cap `Tauth` is refused with `"authentication
    failed"` / `EACCES` **before the authenticator is asked**, so a peer that is guessing does not
    make the server pay for a credential check. A successful attach clears the address. Defaults
    are the server's to choose; this workspace ships metering off, 64 connections and 32 unverified
    authentications per address. An in-process endpoint is exempt from (b) and (c): whoever can
    dial it already runs inside the process. The tracking tables are themselves bounded, so the
    defence cannot become the memory a flood is aiming at.
